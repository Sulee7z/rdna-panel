# 设计说明与依据

这个文件记录 RadeonTune 为什么是现在这个样子，以及哪些是**观察**、哪些是**分析**、哪些是**推理**。

标记：**观察** = 本机复现过；**分析** = 从其构建方式推断；**推理** = 合理但**未实测**。

## 1. 为什么是替换驱动面板，而不是扩展它

- **分析：厂商面板是依托 Windows shell 的 WebView2/浏览器前端。**
  它的窗口属于 shell 进程，界面是 WebView2 渲染的 HTML/JS，数据来自本地服务。后果：
  - Explorer 重启会连带干掉面板；
  - WebView2 进程卡死，面板就白屏或无响应；
  - 面板无法被自动化可靠驱动。
- **观察（作者在本机）：面板偶尔打不开，或显示空白，直到 shell/WebView2 状态被重置。**
- **观察：由驱动 profile 机制保存的超频预设会被覆盖或清除**——驱动更新、配置重载、
  面板重新初始化之后都可能发生，应用过的数值不保证能恢复。

RadeonTune 的应对是结构性的：原生 ADLX/ADL 核心 + 纯 WPF（无 WebView）+ 自己持有的预设文件
（`data/presets.json`）。

## 2. 为什么不做显存超频

**状态：推理，不是实测。** 本项目**没有**做过显存超频实验，也**没有**因此产生过黑屏/白屏。

推理依据：

- 这类显卡改显存频率会触发 **UCLK 切换**（显存控制器换工作点，而不是固定频率）。
- 驱动同时施加**防掉压（load-line 类）电压调节**。
- 动态显存频率叠加这个调节环路，是显示链路失稳（黑屏、白屏）的典型来源。

由于失效边界难以界定，且需要在用户唯一的显卡上做大量高风险实验，功能被有意省略。
核心频率、功耗上限、电压偏移、风扇曲线不涉及 UCLK 切换，因此实现了。

若将来要重做显存调优，实验必须设计好回退显示路径（核显或第二张卡输出）与恢复步骤，
而不是随手加上。

## 3. 这些结论的来源

- 面板架构：对厂商软件打包方式（WebView2 + shell 宿主窗口）的分析，并与本机观察到的行为对照。
- 预设丢失：本机反复出现、用户可见的行为。
- 显存/UCLK：关于显存频率切换如何执行的架构推理；**明确不是测量**，也不当作测量来表述。
